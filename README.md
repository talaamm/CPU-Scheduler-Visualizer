# CPU Scheduler Visualizer

An interactive Operating Systems simulator that visualizes how different CPU scheduling algorithms decide which process runs next — built to turn the abstract theory from an OS course (ready queues, CPU/I/O bursts, preemption, scheduling metrics) into something you can actually watch happen.

Give it a set of processes with CPU and I/O bursts, pick an algorithm, and step through the simulation tick by tick: which process is on the CPU, what's waiting in the ready queue, what's blocked on I/O, and *why* the scheduler made each decision.

## Live Demo

**[cpu-scheduler-visualizer.onrender.com](https://cpu-scheduler-visualizer.onrender.com)** *(fill in after deployment — see Deployment below)*

The API is on Render's free tier, which spins down after 15 minutes of inactivity — the first request after a while may take 30-60s to wake it back up. The UI tells you when that's happening instead of just looking stuck.

## Why this exists

Scheduling algorithms are easy to state ("run the shortest job next") and surprisingly easy to get subtly wrong in practice — tie-breaking, preemption timing, what happens when two processes arrive at the same instant, what happens when a process returns from I/O mid-quantum. I wanted a tool that would let me *see* those edge cases instead of tracing them by hand on paper, and that demonstrates the full backend-simulation-to-frontend-visualization pipeline, not just a scheduling algorithm in isolation.

## Architecture

```
Frontend (Vue 3 + TypeScript)
        │  REST (JSON)
        ▼
API layer (Go net/http)
        │
        ▼
Simulation engine (Go)  ──uses──  Scheduling policy (Go)
```

The simulation engine is deliberately decoupled from scheduling policy: the engine owns time progression, the ready/I/O queues, process state transitions, and metrics — it has no idea what algorithm is running. Each algorithm is just a `SchedulingPolicy` (a `SelectNext` function, an optional `ShouldPreempt` function, an optional time quantum, and an `Explain` function that produces the human-readable reason for its own decisions). This is what lets six different policies share one tested engine instead of six copy-pasted simulators.

```
core/         Process, Burst, ProcessState — the data model
simulation/   the engine: arrivals, CPU execution, I/O queue, ready queue,
              metrics, and a real per-tick state snapshot + event log
algorithms/   FCFS, SJF, SRTF, Round Robin, Priority (NP & P) — each just
              a SchedulingPolicy plugged into the shared engine
backend/      REST API (net/http, no framework) exposing simulate/compare
frontend/     Vue 3 + Pinia + TypeScript SPA
tests/        golden-trace tests per algorithm, verified against
              hand-worked reference traces in tests/run-example/
```

## Supported algorithms

| Algorithm | Preemptive | Notes |
|---|---|---|
| FCFS | No | Arrival order. Simple, but suffers from the convoy effect. |
| SJF | No | Shortest next CPU burst runs first. Optimal average waiting time, requires knowing burst lengths in advance. |
| SRTF | Yes | Preemptive SJF — preempts whenever a process with less remaining time becomes ready. |
| Round Robin | Yes (quantum) | Fixed time slice, cyclic. Fairness depends heavily on quantum size. |
| Priority (Non-Preemptive) | No | Highest priority runs to completion once started. Can starve low-priority processes. |
| Priority (Preemptive) | Yes | Preempts immediately when a higher-priority process arrives. |

Lower priority *value* = higher priority, matching the usual OS-course convention.

## How the simulation works

Each `Simulation.Step()` call advances the clock by one tick:

1. **Arrivals** — any process whose arrival time has passed enters the ready queue.
2. **I/O completion** — any process whose I/O burst has finished returns to the ready queue (or terminates, if that I/O burst was its last one).
3. **Preemption check** — the active policy's `ShouldPreempt` decides whether a ready process should take over the CPU.
4. **Selection** — if the CPU is idle, the active policy's `SelectNext` picks the next process.
5. **Execution** — the running process's remaining burst time decrements by one; burst/quantum completion is handled here.

At every tick the engine records a **state snapshot** (exact ready queue, I/O queue, and running process — not reconstructed after the fact) and any **events** (`ARRIVED`, `SELECTED`, `PREEMPTED`, `IO_START`, `IO_DONE`, `COMPLETED`), each carrying a message generated by the algorithm itself (e.g. *"P2 preempted P1 — remaining time 3 < 4"*). The frontend's Live View and Gantt tooltips render this data directly — it doesn't guess at what the scheduler was thinking.

## Main features

- **Process builder** — add processes with arbitrary CPU/I/O burst sequences, arrival times, and priorities.
- **Gantt chart** — SVG timeline with a live animated cursor and hover explanations for every decision.
- **Live simulation view** — CPU, ready queue, and I/O queue rendered from real engine state, with playback controls (play/pause/step/scrub/speed).
- **Metrics dashboard** — per-process waiting/turnaround/response time, plus CPU utilization and throughput.
- **Algorithm comparison** — run the same workload through multiple algorithms and compare metrics side by side, ranked.
- **Built-in presets** — classic textbook workload, I/O-heavy workload, a starvation scenario, and a pure-CPU-burst workload.

## Example workflow

1. Load the "Classic Textbook" preset (3 processes, mixed CPU/I/O bursts).
2. Run it under FCFS — watch P1 hog the CPU while P2 and P3 wait (the convoy effect).
3. Switch to SRTF on the same workload — watch preemption happen the instant a shorter job becomes ready.
4. Switch to the Compare view and run FCFS, SJF, SRTF, and Round Robin together — see average waiting time drop as the algorithm gets smarter, and CPU utilization dip where a scheduler leaves gaps.

## What I learned / debugged

Building the shared-engine-plus-pluggable-policy design paid off: once FCFS's engine plumbing (arrivals, I/O queue, ready queue, metrics) was correct, SJF/SRTF/RR/Priority were each only a few lines of selection logic. I verified all six against hand-worked Gantt traces (`tests/run-example/`) before trusting them, then locked that in as automated golden-trace tests.

The most interesting bug I found: a process whose **last** burst is I/O (rather than CPU) was silently dropped by the engine instead of being marked complete, which made the simulation loop forever. It only showed up because I was validating an edge case the textbook examples don't cover — a good reminder that "matches the textbook trace" and "correct for all valid input" aren't the same thing.

A second one showed up while stress-testing the UI before deployment: re-running a simulation while a previous one's Gantt-chart animation was still playing leaked a `setInterval` — the playback store cleared the `isPlaying` flag but never actually cancelled the timer, so each leaked interval kept ticking the clock forward on its own. Fixed by routing every reset through the same `pause()` path that owns the interval handle, instead of duplicating that cleanup inline.

## Deployment

```
Browser
   │
   ▼
Static frontend (Render Static Site)        Vue 3 build output, served over HTTPS
   │  fetch() → VITE_API_URL
   ▼
Go REST API (Render Web Service, free tier) same engine as local dev, PORT from env
```

Both services deploy from this repo via the `render.yaml` Blueprint — one Render account, no credit card, auto-deploy on every push to `main`:

- **Frontend** — Render Static Site, builds `frontend/` with `npm install && npm run build`, serves `frontend/dist`. `VITE_API_URL` is baked in at build time.
- **Backend** — Render Web Service (free), builds the Go binary, listens on the `PORT` Render assigns. `ALLOWED_ORIGINS` locks CORS down to the deployed frontend's exact origin (wide-open `*` is only the local-dev default).
- **No database** — the simulator is stateless; every request computes a fresh result.

The free web service spins down after 15 minutes idle (a cold request takes 30-60s to wake it) — expected for a low-traffic portfolio demo, not a bug. The app surfaces this in the UI rather than looking broken.

## Running it locally

**Backend:**
```bash
go run ./backend/cmd/server
# API on http://localhost:8080
```

**Frontend:**
```bash
cd frontend
npm install
npm run dev
# App on http://localhost:5173 (proxies /api to the Go server)
```

**Tests:**
```bash
go test ./...
```

There's also a standalone, no-build-step demo (`cpu-scheduler-visualizer.html`) that the Go server serves directly at `/` — useful for a quick look without running the Vite dev server, though the Vue app under `frontend/` is the actively developed version.
